# Technical debt register

Deliberate shortcuts, recorded when taken rather than discovered later. Each
entry names the trade-off and what would trigger paying it off.

| # | Debt | Taken in | Why | Trigger to pay it off |
|---|---|---|---|---|
| 1 | PHPStan does not analyse `tests/Feature`, `tests/Unit` — and, since Phase 7, `tests/Arch` | Phase 1, extended Phase 7 | Pest binds `$this` in test closures at runtime; PHPStan sees `Pest\PendingCalls\TestCall` and flags every `$this->getJson()` — and every `arch()->preset()` the same way. The fix, `pestphp/pest-plugin-phpstan`, needs Pest 5 → PHPUnit 13, and Laravel 13 pins PHPUnit 12. Test-support classes (`tests/Support`, the concurrency harness included) are real classes and stay analysed at level 7. | Laravel 13 supports PHPUnit 13, or Pest backports the plugin. |
| 2 | Tests run against SQLite in-memory, production is MySQL 8.4 | Phase 1 | Keeps the suite at seconds of wall clock and hermetic on a laptop. | **Paid off in Phase 7:** the nightly CI job runs the entire suite with MySQL as the default connection (plus the concurrency group against a served app on MySQL on every push). Its first run caught three MySQL-only bugs — a too-short status column, JSON key-order normalization under the mock PSP's byte-for-byte replay, and fractional-second ROUNDING that made ~half of grace-period notifications look stale (docs/ci.md). SQLite remains the push-CI speed tier by design. |
| 3 | No production image target — the Dockerfile is dev-only (bind mount, `opcache.validate_timestamps=1`, source not baked in) | Phase 1 | Nothing deploys yet. | Phase 9, with the zero-downtime deploy pipeline. |
| 4 | Horizon dashboard has no authorization gate beyond the default `web` middleware | Phase 1 | Local only, not exposed. | Before anything is deployed anywhere reachable. `HorizonServiceProvider::gate()` is already scaffolded and empty. |
| 5 | `subscriptions` allows more than one row per (user, product) | Phase 1 | MySQL has no partial unique index, and "one *active* subscription per product" is a state-machine invariant, not a column constraint. | **Paid off in Phase 3:** enforced by `CreatePaymentIntent` (granting subscription → 409, incomplete/canceled row reused) + the state machine's allow-list; resubscribe-after-cancel is covered by tests. |
| 6 | `/health` is unauthenticated and unthrottled: it names infrastructure detail (eviction policies, drivers) and costs four dependency round-trips per hit | Phase 1 | Local only, and a probe must not depend on the auth or rate-limit infrastructure it exists to check — restricting it is a network-layer job, not a middleware one. | Before anything is deployed anywhere reachable: expose `/health` only to the load balancer / internal network, exactly like the Horizon gate in debt #4. |
| 7 | API auth is one static bearer token per surface (ingest, billing) | Phase 2–3 | The ingest hot path does auth + envelope validation only; per-product credentials, rotation and scoping belong with the API/auth work (Module 8). | Before any producer outside local dev: per-product keys with rotation, and the token comparison moves to a keyed lookup. |
| 8 | `events_archive` uniqueness is `(event_id, received_at)`, not `event_id` alone | Phase 2 | MySQL requires the partition column in every unique key. A duplicate could theoretically land twice with different `received_at` values — in practice only if a producer retries the same event_id after the dedup TTL (15 min) *and* the retries straddle different ingest seconds. | If reconciliation or projections ever observe a cross-second duplicate in the archive; the fix is a small unpartitioned `event_id → month` lookup table, at the cost of one extra insert per event. |
| 9 | The reaction map ships empty — the reactions consumer runs with nothing wired | Phase 2 | Domain reactions need billing *events flowing through the pipeline*, which arrive with the Phase 5 outbox (billing publishes, reactions consume). The machinery (markers, at-least-once dispatch, idempotency contract) is built and tested with a fake job. | **Paid off in Phase 5:** the outbox relay republishes billing domain events into the pipeline and the `billing.*` types dispatch `ProjectBillingMetric` — the first real reaction, exactly-once via consumption markers (`ConsumeOnce`). |
| 10 | The PSP webhook endpoint verifies HMAC and queues, nothing more — no timestamp tolerance, no raw persistence, no provider-event-id unique key | Phase 3 | Duplicate/reordered deliveries are already fully absorbed one layer down (`ApplyChargeOutcome` + ledger unique keys, ADR-004), so the edge hardening is sequencing, not a correctness hole. | **Paid off in Phase 4:** `t=…,v1=…` HMAC over timestamp + raw bytes with ±5 min tolerance → `webhook_events` persisted raw under `UNIQUE(provider, provider_event_id)` → 200 → dispatch on `status = pending` (not on "just inserted"); stale-transition rejection by the store's clock (`SubscriptionStateMachine::mirror`); hourly bidirectional reconciliation with a pending-webhook reaper. |
| 11 | IAP money is not in the ledger: Apple/Google revenue, commission and payouts are not booked | Phase 4 | The stores collect, net their cut and pay out on their own statements (ADR-005). Booking "IAP revenue" from notifications would be a second set of books that disagrees with the first by construction. | When IAP revenue recognition is required: payout reconciliation from App Store / Play financial reports, as their own ledger accounts, in its own phase. |
| 12 | App Store notifications are verified against a pinned ES256 public key, not the `x5c` chain to the Apple Root CA G3 | Phase 4 | The mock store signs with a dev key; pinning its public half exercises every byte of the verification path except the chain walk. Same trust decision, one fewer hop. | Before any real App Store traffic: verify the `x5c` chain to the bundled Apple root, check the leaf's OID, and rotate on Apple's schedule. |
| 13 | Google RTDN push is authenticated by the Pub/Sub URL verification token, not the OIDC JWT | Phase 4 | The body is never believed (the handler re-fetches from the Play API), so a forged push can only cause a harmless re-read; the token stops casual noise. | Before any real Play traffic: validate the push's OIDC token (`aud`, service-account `email`) against Google's certs. |
| 14 | Store re-sync re-fetches every live store-backed subscription every hour, one API call each | Phase 4 | Correct and simple at capstone scale; it also advances every watermark hourly, which is what makes late notifications provably stale. | Store API quota pressure or thousands of live IAP rows: batched status endpoints (Apple "Get All Subscription Statuses"), and re-sync rows whose period end is far away less often. |
| 15 | Reconciliation alerts are `Log::critical` on the unresolved count, nothing pages | Phase 4 | Same posture as `events:check-lag` (debt from ADR-003's one-person operational budget): the run is persisted in `reconciliation_runs` with per-finding counts, so the metric exists before the pager does. | Phase 9: export `reconciliation_runs` to Prometheus and page on `unresolved > 0` and on a rising `fixed` rate. |
| 16 | Domain events ride the behavioral event stream — one buffer, one backpressure policy | Phase 5 | No second bus to operate: the outbox relay reuses the hardened Phase 2 pipeline (archive, groups, DLQ, lag watchdog), and the outbox table itself buffers domain events durably while ingest rejects. Operational priority already exempts them from shedding. | Billing reaction lag that moves with client-event volume: give domain events their own stream via the `EventBuffer` seam (ADR-006); Phase 6 measures the interference. |
| 17 | Consumption markers (`domain_event_consumptions`) are pruned after 30 days | Phase 5 | Unbounded dedup memory is a table that only grows; 30 days comfortably exceeds every honest redelivery horizon (stream retention, queue retries, routine dead-letter replay). | Replaying events older than the marker horizon becomes a real operation: extend the retention or archive markers with the events, BEFORE replaying — a pruned marker is a reopened dedup window. |
| 18 | The outbox relay polls MySQL (500ms idle interval), not CDC/binlog tailing | Phase 5 | A polling relay is ~100 readable lines with no new infrastructure; SKIP LOCKED makes it parallel-safe. Delivery latency floors at the poll interval, which nothing downstream currently feels. | A latency SLO under the poll interval, or measurable DB load from relay polling at scale: switch to log tailing (Debezium-style) behind the same outbox table. |
| 19 | Queue alerts (`LongWaitDetected`, `QueueBusy`) are `Log::critical`, nothing pages | Phase 6 | Same posture as reconciliation alerting (#15) and the lag watchdog: the thresholds, events and listeners exist, so wiring a pager is configuration, not design. | Phase 9: route both through the alerting stack with the SLO work; a wait-time breach on `payments:payments` becomes a page, the volume lanes become tickets. |
| 20 | All three queue lanes share one physical Redis instance — isolation is by supervisor/connection, not hardware (ADR-007) | Phase 6 | The flood demo shows worker-pool isolation holds at 1M queued jobs; separate instances would add two more processes to a one-person operational budget for contention nobody has measured. | Payments wait time correlating with events/bulk depth, or the queue instance nearing its memory/CPU ceiling under real load: point the `payments` connection at its own instance — a config edit by design. |
| 21 | The concurrency rig serves the app with PHP's built-in server (`php -S`, 25 workers), not FPM/nginx | Phase 7 | Real parallelism against real MySQL locks is what the test needs, and the dev server provides it hermetically per pest run; FPM would add config and teardown for no extra truth about *locking*. | If a concurrency bug ever hinges on FPM semantics (opcache sharing, request termination mid-transaction): point the harness at the compose app container instead — the burst and the assertions stay identical. |
| 22 | Chaos seeds vary only in the nightly roulette (5/night); push CI runs the fixed defaults | Phase 7 | Push CI must never flake; a seeded failure found overnight reproduces exactly via `CHAOS_SEED`. Five orderings a night compounds to wide coverage within weeks. | A chaos-group invariant failure that nightly misses but production hits: raise the nightly multiplier, or move to a property-testing loop with shrinking. |
| 23 | A deliberately arm-able cross-request leak ships in the codebase (`OCTANE_DEMO_CROSS_REQUEST_LEAK`: singleton binding switch in AppServiceProvider + warm splice in config/octane.php) | Phase 8 | A leak detector that has never detected a leak proves nothing: the interleaved-user test asserts the planted bug is *caught*, and the live demo is one env var (ADR-008). Default-off, and off means the flag's code paths reduce to `scoped()`. | If the demo seam ever complicates a real change to the ActingUser binding, replace the config switch with a test-only container rebind and delete the flag. |
| 24 | Octane worker mode in dev means code and .env edits need `docker compose restart app` — no file watcher configured | Phase 8 | The same discipline the Horizon/worker containers always required, now including the app. FrankenPHP's `watch` directive exists, but a dev-only auto-restart differing from production behavior is its own class of confusion. | If the restart step demonstrably eats dev time: add `watch` lines to FRANKENPHP_CONFIG in an opt-in compose override, never in the default. |
| 25 | Production PHP/OPcache posture (`validate_timestamps=0`, `artisan optimize` baked at build) is measured but not shipped — the dev image stays edit-friendly | Phase 8 | The deltas are recorded per rung in docs/load-tests.md, so the production image is an assembly job, not a research job. Under worker mode both mostly move worker *boot* cost anyway (rung D′ = rung D). | Phase 9's production image target (with debt #3): bake `optimize` + `validate_timestamps=0` into the deploy image and keep the dev compose as is. |
