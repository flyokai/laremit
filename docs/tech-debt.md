# Technical debt register

Deliberate shortcuts, recorded when taken rather than discovered later. Each
entry names the trade-off and what would trigger paying it off.

| # | Debt | Taken in | Why | Trigger to pay it off |
|---|---|---|---|---|
| 1 | PHPStan does not analyse `tests/Feature` and `tests/Unit` | Phase 1 | Pest binds `$this` in test closures at runtime; PHPStan sees `Pest\PendingCalls\TestCall` and flags every `$this->getJson()`. The fix, `pestphp/pest-plugin-phpstan`, needs Pest 5 → PHPUnit 13, and Laravel 13 pins PHPUnit 12. | Laravel 13 supports PHPUnit 13, or Pest backports the plugin. |
| 2 | Tests run against SQLite in-memory, production is MySQL 8.4 | Phase 1 | Keeps the suite at sub-second wall clock and hermetic on a laptop. | Phase 7 CI adds a MySQL job for the nightly run; anything touching partitions, `SKIP LOCKED` or `READ COMMITTED` semantics must be tested there, not on SQLite. |
| 3 | No production image target — the Dockerfile is dev-only (bind mount, `opcache.validate_timestamps=1`, source not baked in) | Phase 1 | Nothing deploys yet. | Phase 9, with the zero-downtime deploy pipeline. |
| 4 | Horizon dashboard has no authorization gate beyond the default `web` middleware | Phase 1 | Local only, not exposed. | Before anything is deployed anywhere reachable. `HorizonServiceProvider::gate()` is already scaffolded and empty. |
| 5 | `subscriptions` allows more than one row per (user, product) | Phase 1 | MySQL has no partial unique index, and "one *active* subscription per product" is a state-machine invariant, not a column constraint. | **Paid off in Phase 3:** enforced by `CreatePaymentIntent` (granting subscription → 409, incomplete/canceled row reused) + the state machine's allow-list; resubscribe-after-cancel is covered by tests. |
| 6 | `/health` is unauthenticated and unthrottled: it names infrastructure detail (eviction policies, drivers) and costs four dependency round-trips per hit | Phase 1 | Local only, and a probe must not depend on the auth or rate-limit infrastructure it exists to check — restricting it is a network-layer job, not a middleware one. | Before anything is deployed anywhere reachable: expose `/health` only to the load balancer / internal network, exactly like the Horizon gate in debt #4. |
| 7 | API auth is one static bearer token per surface (ingest, billing) | Phase 2–3 | The ingest hot path does auth + envelope validation only; per-product credentials, rotation and scoping belong with the API/auth work (Module 8). | Before any producer outside local dev: per-product keys with rotation, and the token comparison moves to a keyed lookup. |
| 8 | `events_archive` uniqueness is `(event_id, received_at)`, not `event_id` alone | Phase 2 | MySQL requires the partition column in every unique key. A duplicate could theoretically land twice with different `received_at` values — in practice only if a producer retries the same event_id after the dedup TTL (15 min) *and* the retries straddle different ingest seconds. | If reconciliation or projections ever observe a cross-second duplicate in the archive; the fix is a small unpartitioned `event_id → month` lookup table, at the cost of one extra insert per event. |
| 9 | The reaction map ships empty — the reactions consumer runs with nothing wired | Phase 2 | Domain reactions need billing *events flowing through the pipeline*, which arrive with the Phase 5 outbox (billing publishes, reactions consume). The machinery (markers, at-least-once dispatch, idempotency contract) is built and tested with a fake job. | Phase 5: the outbox publishes billing domain events and the first real reactions consume them. |
| 10 | The PSP webhook endpoint verifies HMAC and queues, nothing more — no timestamp tolerance, no raw persistence, no provider-event-id unique key | Phase 3 | Duplicate/reordered deliveries are already fully absorbed one layer down (`ApplyChargeOutcome` + ledger unique keys, ADR-004), so the edge hardening is sequencing, not a correctness hole. | **Paid off in Phase 4:** `t=…,v1=…` HMAC over timestamp + raw bytes with ±5 min tolerance → `webhook_events` persisted raw under `UNIQUE(provider, provider_event_id)` → 200 → dispatch on `status = pending` (not on "just inserted"); stale-transition rejection by the store's clock (`SubscriptionStateMachine::mirror`); hourly bidirectional reconciliation with a pending-webhook reaper. |
| 11 | IAP money is not in the ledger: Apple/Google revenue, commission and payouts are not booked | Phase 4 | The stores collect, net their cut and pay out on their own statements (ADR-005). Booking "IAP revenue" from notifications would be a second set of books that disagrees with the first by construction. | When IAP revenue recognition is required: payout reconciliation from App Store / Play financial reports, as their own ledger accounts, in its own phase. |
| 12 | App Store notifications are verified against a pinned ES256 public key, not the `x5c` chain to the Apple Root CA G3 | Phase 4 | The mock store signs with a dev key; pinning its public half exercises every byte of the verification path except the chain walk. Same trust decision, one fewer hop. | Before any real App Store traffic: verify the `x5c` chain to the bundled Apple root, check the leaf's OID, and rotate on Apple's schedule. |
| 13 | Google RTDN push is authenticated by the Pub/Sub URL verification token, not the OIDC JWT | Phase 4 | The body is never believed (the handler re-fetches from the Play API), so a forged push can only cause a harmless re-read; the token stops casual noise. | Before any real Play traffic: validate the push's OIDC token (`aud`, service-account `email`) against Google's certs. |
| 14 | Store re-sync re-fetches every live store-backed subscription every hour, one API call each | Phase 4 | Correct and simple at capstone scale; it also advances every watermark hourly, which is what makes late notifications provably stale. | Store API quota pressure or thousands of live IAP rows: batched status endpoints (Apple "Get All Subscription Statuses"), and re-sync rows whose period end is far away less often. |
| 15 | Reconciliation alerts are `Log::critical` on the unresolved count, nothing pages | Phase 4 | Same posture as `events:check-lag` (debt from ADR-003's one-person operational budget): the run is persisted in `reconciliation_runs` with per-finding counts, so the metric exists before the pager does. | Phase 9: export `reconciliation_runs` to Prometheus and page on `unresolved > 0` and on a rising `fixed` rate. |
